ACCEPTANCE TEST: REVIEW WITH NO AWS CREDENTIALS REACHABLE
========================================================================

Credentials on this machine do not come from environment variables. The dnrec
profile uses a credential_process, so unsetting AWS_ACCESS_KEY_ID alone would
prove nothing. This test blocks every credential source:

    AWS_CONFIG_FILE             pointed at a nonexistent path
    AWS_SHARED_CREDENTIALS_FILE pointed at a nonexistent path
    AWS_EC2_METADATA_DISABLED   true, so instance metadata cannot answer
    AWS_ACCESS_KEY_ID           unset
    AWS_SECRET_ACCESS_KEY       unset
    AWS_SESSION_TOKEN           unset
    AWS_PROFILE                 unset
    AWS_DEFAULT_PROFILE         unset

Proof the block worked, before running any review:

    credentials found: NONE
    STS failed as expected: NoCredentialsError

RESULT: all three cached examples produced a complete report.

    permit_281364_60839580   13 pages   CANNOT VERIFY   0 pass / 0 fail / 15 unknown
      10 values read, 9 missing, 3 readings discarded
    permit_282133_60843649    1 page    CANNOT VERIFY   0 pass / 0 fail / 15 unknown
      4 values read, 14 missing, 1 reading discarded
    permit_282863_60847038   19 pages   CANNOT VERIFY   0 pass / 0 fail / 15 unknown
      7 values read, 12 missing, 4 readings discarded

Each run wrote review_<name>.txt, .html and .json and reported:

    source          cached Textract analysis (no network used)
    no network was used: the Textract analysis came from the disk cache

Also tested without the --offline flag, since someone may forget it on the day.
The run completed in 2.5 seconds, produced the same verdict, and disclosed that
the precedent list fell back to the offline stand-in embedder rather than
presenting it as a semantic match.

The verdict is CANNOT VERIFY because no rule has been certified by a person, not
because anything failed. That is the interlock working.
